# Mercado Pago integration research (Brazil)

Research date: 2026-10-20. Sources are Mercado Pago Developers documentation only. The recommendation below is for replacing the existing AbacatePay adapter while preserving the branch's order, entitlement, return-page, webhook, and idempotency behavior.

## Recommended product split

### One-time document purchase: Checkout Pro Preferences

Use the backend to create a Mercado Pago preference (`POST /checkout/preferences`) with one item, a stable `external_reference` containing the internal order ID, `notification_url`, and `back_urls.success`, `back_urls.pending`, and `back_urls.failure`. The response contains `init_point`; redirect the browser to that hosted Mercado Pago checkout. Checkout Pro is explicitly a redirect checkout and the preference defines the item, amount, payment methods and return URLs ([Preferences API reference](https://www.mercadopago.com.br/developers/en/reference/online-payments/checkout-pro-preferences/overview), [return URLs](https://www.mercadopago.com.br/developers/pt/docs/checkout-pro-preferences/configure-back-urls)). This gives the product both Pix and card options without storing card data in DocFácil.

The return URL is only a user-navigation signal. After a redirect or a webhook, load the Checkout Pro payment from Mercado Pago using the server-side Access Token and the ID/reference, then reconcile it with the local order. For this Preferences flow, grant document access only after the authoritative payment status is `approved` and the amount, currency, and `external_reference` match. Do not use the Orders API status `processed` as a substitute; that status belongs to a different Orders integration. The Checkout Pro notification documentation demonstrates looking up the payment ID received in the notification ([payment notifications](https://www.mercadopago.com.br/developers/en/docs/checkout-pro-preferences/payment-notifications)).

### Monthly Pro: Subscriptions API (`/preapproval`)

Create a customer-specific subscription through `POST /preapproval` (or create a reusable plan and attach the subscription). Set monthly frequency and amount, use a success/return URL, and persist the returned `preapproval` ID alongside the local user/entitlement. Mercado Pago describes this API as automatic recurring charges with configurable frequency and retries ([Subscriptions overview](https://www.mercadopago.com.br/developers/en/docs/subscriptions/overview), [Subscriptions API reference](https://www.mercadopago.com.br/developers/pt/reference/online-payments/subscriptions/overview)). Do not assume that every payment method shown in the general overview is available for every recurring configuration; confirm the account and subscription method in the API response. A subscription being created is not proof that its first charge was approved.

Enable the subscription topics `subscription_preapproval` (subscription creation/update) and `subscription_authorized_payment` (recurring invoice creation/update), and also `payment` for the payments associated with subscriptions. For `subscription_preapproval`, query `/preapproval/search` or the specific subscription; for `subscription_authorized_payment`, query `/authorized_payments/{id}` for invoice data; for `payment`, query `/v1/payments/{id}` ([official notification topics and lookup URLs](https://www.mercadopago.com.br/developers/en/docs/links-and-debts/additional-content/your-integrations/notifications/webhooks)).

For recurring card charges that are implemented through the Automatic Payments/Orders flow instead of `/preapproval`, Mercado Pago requires recurring metadata (`stored_credentials.reason = recurring`, or the corresponding `automatic_payments.subscription` fields) and a customer/payment profile. That is a lower-level alternative and should not be mixed with the `/preapproval` flow in the first migration ([scheduled recurring payments](https://www.mercadopago.com.br/developers/en/docs/automatic-payments-orders/process-recurring-payments), [create recurring charges](https://www.mercadopago.com.br/developers/en/docs/automatic-payments/recurring-charges)).

## Webhook receiver and reconciliation

Expose a public HTTPS POST endpoint (for example `/api/payments/mercadopago/webhook`). Configure the Payments and, if using Orders, `orders_v2` topics in the Mercado Pago application; a preference may also provide a per-transaction `notification_url` ([configure notifications](https://www.mercadopago.com.br/developers/en/docs/checkout-pro-preferences/payment-notifications)).

Validate the notification before parsing or mutating state. Mercado Pago sends an `x-signature` header containing `ts` and `v1`, plus `x-request-id`; the documented validator derives the signed message from the notification's `data.id` and compares the HMAC signature with the application secret ([Webhooks signature validation](https://www.mercadopago.com.br/developers/en/docs/links-and-debts/additional-content/your-integrations/notifications/webhooks)). Keep the raw request body available, parse the signature fields, use constant-time comparison, and return 401 for an invalid signature. The documentation explicitly excludes QR Code notifications from secret-signature validation, so QR flows need the provider's documented alternative controls. Do not treat a webhook payload's status as sufficient: use the received payment, subscription, or authorized-payment ID to GET the current resource with the Access Token, and only then update the local order/subscription.

Use idempotency at two layers. For each outbound logical operation, generate one UUID `X-Idempotency-Key`; retrying that same operation must reuse the same key, while a new operation gets a new key. Mercado Pago documents this header as mandatory for Orders writes and refunds, and returns a conflict if the same key is reused with a different body ([Payments-to-Orders migration and idempotency](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/resources/migrate-payments-to-orders), [refund API](https://www.mercadopago.com.br/developers/en/reference/online-payments/checkout-api-payments/create-refund/post)). For incoming events, deduplicate the financial effect by provider resource (especially payment ID) and make transitions monotonic/idempotent. Do not permanently ignore `(topic, resource_id, action)` duplicates: a later `payment.updated` can legitimately move `pending` to `approved`. Store every notification for audit, and apply each newly observed provider status in a transaction with a unique constraint on the resulting effect.

## Cancellation, refunds, and chargebacks

Keep internal order state separate from provider state. For a payment that is still `in_process`, `pending`, or `authorized`, the Payments API cancellation is `PUT /v1/payments/{payment_id}` with `{ "status": "cancelled" }` ([cancel payment](https://www.mercadopago.com.br/developers/pt/reference/online-payments/checkout-api-payments/create-cancellation/put)). For a captured payment, use `POST /v1/payments/{id}/refunds`; omit `amount` for a full refund or provide it for a partial refund, always with `X-Idempotency-Key` ([create refund](https://www.mercadopago.com.br/developers/pt/reference/online-payments/checkout-pro/create-refund/post)). If the implementation chooses Orders API instead, use `/v1/orders/{order_id}/cancel` before completion and `/v1/orders/{order_id}/refund` after processing; Orders write operations require idempotency ([Orders integration model](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/integration-model)).

Subscribe to chargeback notifications and persist a chargeback case. A chargeback can withdraw funds after a customer disputes a card charge; Mercado Pago may require evidence through its API ([chargebacks](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/payment-management/chargebacks)). A chargeback should revoke or suspend the local entitlement according to the business policy, and should never be treated as an ordinary refund.

## Sandbox and test constraints

Use Mercado Pago test credentials and separate seller/buyer test accounts; seller/buyer accounts must be in the same country ([test accounts](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/resources/test-accounts)). For cards, use the official test cards and cardholder status values such as `APRO` (approved), `CONT` (pending), `OTHE` (generic rejection), and `DUPL` (duplicate). The SDK/API does not use a runtime “sandbox flag”; the test credential activates the test environment ([card integration tests](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/integration-test/cards)). Test Pix, pending, rejection, duplicate webhook delivery, and refund/cancel paths separately; verify each result with a GET to the provider API and the local database.

If the existing AbacatePay UX must keep an in-app QR/Pix Copia-e-Cola screen, use Checkout Transparente's Pix flow instead of Checkout Pro for that payment method. Creating an order returns `ticket_url`, `qr_code`, and `qr_code_base64`; the frontend can render the QR and copy code while the order remains awaiting payment ([Pix QR/link integration](https://www.mercadopago.com.br/developers/en/docs/checkout-api-orders/payment-integration/websites/pix?scope=prod)). This is an Orders/Checkout Transparente integration with different statuses and write endpoints; keep it behind a separate adapter and do not mix its `processed` status into the Checkout Pro Preferences path.

Do not claim production readiness from a local redirect test. Production requires an HTTPS webhook URL, production credentials, a configured application secret, a reconciliation job for missed notifications, and verified return URLs. Mercado Pago's notification configuration allows a test URL and production URL, but signature validation and API re-fetch remain required in both environments.

## Migration shape from AbacatePay

Preserve the existing domain concepts (`orders`, payment status transitions, one-time entitlement, Pro entitlement, webhook event ledger, and idempotency constraints). Replace only provider-specific code behind a Mercado Pago gateway:

1. `createOneTimeCheckout(order)` creates a Checkout Pro preference and returns `init_point`.
2. `createProSubscription(user)` creates `/preapproval` and persists its provider ID.
3. `handleMercadoPagoWebhook(request)` validates `x-signature`, deduplicates, GETs the resource, then applies a transaction-safe transition.
4. `getPaymentStatus`/`getSubscriptionStatus` are server-side API reads used by return pages and reconciliation.
5. `cancelPayment`, `refundPayment`, and (if needed) `cancelSubscription` call the corresponding API with fresh idempotency keys.

Keep secrets server-only (`MP_ACCESS_TOKEN`, webhook secret, and any subscription configuration). The browser receives only a hosted checkout URL or a public key where the chosen frontend SDK requires one.
